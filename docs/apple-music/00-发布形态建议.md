> 一句话摘要：本项目的改动已深入上游核心文件，只能以 **独立 fork + AGPL-3.0 整包分发** 的形式发布；模组化在现有实现下不可行，向上游提 PR 不是当前值得投入的路径。

## 2. 三种发布形态逐项对比

### 2.1 独立 fork 分发（推荐）

**可行性：高。**

本项目在上游源码基础上直接修改并整包构建，产物是一个可以独立运行的 Windows 应用。这天然就是 fork 分发。

**AGPL-3.0 下的义务（必须全部满足）：**

1. **整包以 AGPL-3.0 分发。** 你不能换许可证，也不能给衍生作品加「禁止商用」「禁止再分发」之类附加限制。
2. **保留上游版权声明。** `LICENSE` 原文保留，不得删除或替换；上游源码文件头部的版权/许可注释也要保留。
3. **显著标注「已修改」。** 每个被改动的源文件要有修改痕迹（Git 提交历史即是证据），并在 README/NOTICE 中说明「本项目基于上游修改而来」。
4. **提供完整对应源码（Corresponding Source）。** 分发二进制（安装包、免安装包）时，必须让接收者能拿到**构建该二进制所用的完整源码**，包括你的改动。
5. **网络服务条款（AGPL 第 13 条）。** 如果你把修改版作为网络服务提供给他人使用，必须向使用者提供获取对应源码的方式。本项目是本地桌面应用，通常不触发，但如果你将来做云端/远程控制版本，这条就会生效。
6. **不额外限制。** 不得对上游代码施加比 AGPL 更严格的条款（例如「不得用于商业用途」）。

**风险：**

- 低。唯一常见误操作是把上游代码说成自己原创，或删掉上游版权声明——这两点本文档全程规避。
- 另一个需要自觉的边界：本项目通过用户自己的浏览器会话操作 Apple Music 网页版，**不涉及解密、不绕过 DRM、不批量抓取受版权保护内容**。文档中只描述到「依赖用户自身的订阅与登录态」这一层，不提供任何绕过手段。

### 2.2 模组化 / 插件形式发布

**可行性：低。**

现状是改动分布在多个上游核心文件中，且相互耦合。已知的侵入点包括（均在 `03-改动原理.md` 中展开）：

- 应用入口与全局装配（`src/App.tsx`）
- 播放队列控制器（`usePlaybackQueueController`）
- 舞台播放控制器（`useStagePlaybackController`）
- 在线音源适配层（`src/services/onlineMusic/*`）
- 账号/平台规则（`src/library/core/model/accountRules.ts` 等）
- Electron 主进程（`electron/main.cjs`、`electron/appleMusic*.cjs`）及新增的 `electron/nowplaying/*`

要把这些拆成「插件不碰上游代码」，必须先在上游里做一轮抽象（例如统一的音源 Provider 接口、播放后端接口、登录流程钩子）。这本身就是一个独立的上游重构项目，工作量大于写完这套文档，而且一旦上游继续演进，你会同时维护「上游重构分支」和「功能分支」两条线。

**判断：现阶段不做。** 但如果将来要把 Apple 逻辑抽出来，建议按 2.4 的目录约定先收敛代码，降低未来抽取成本。

### 2.3 向上游提 PR

**可行性：低–中。**

- 技术层面：改动量大、跨越前端与 Electron 主进程、还引入了一个新的外部服务进程（now-playing 桥），上游评审成本高。
- 产品层面：上游是否愿意接受「接入第三方商业音乐服务的网页端」这一方向，属于产品决策，不是代码质量问题。
- 合规层面：该功能依赖 Apple Music 网页版与用户自身订阅。上游可能出于服务条款或支持成本的考虑拒绝；也可能提出把功能做成可选插件、默认关闭。
- 收益：若被接受，你不必长期维护分叉。若被拒，你仍要维护分叉——所以先按 fork 发布，等实现稳定、抽象清晰后再谈 PR，是更稳的顺序。

**判断：当前不建议投入。** 文档保留 `06-PR-说明与模板.md`，供你将来真的想提时用（成本很低，一篇 Markdown）。

### 2.4 四种形态对照表

| 维度 | 独立 fork | 模组化 | 提 PR 回上游 |
| --- | --- | --- | --- |
| 与现状匹配度 | 完全匹配 | 需先重构上游 | 需先收敛成「上游愿意收的样子」 |
| AGPL 义务 | 全套（源码、声明、标注） | 全套 | 若被合并则成为上游一部分 |
| 额外工作量 | 写文档 + 发布流程 | 高（抽象层重构） | 中（评审往返、风格适配） |
| 维护成本 | 上游更新时需跟进合并 | 中 | 低（若被合并） |
| 风险 | 低 | 高（拆不干净就双线维护） | 中（方向不被接受） |
| 结论 | **选它** | 不做 | 暂不做，留模板 |

## 3. 推荐方案与落地要点

### 3.1 仓库形态

**完整 fork**（保留上游全部提交历史），理由：

- 上游更新时可以直接 `git fetch upstream && git merge`，冲突处理有完整历史可查；
- 上游版权与历史贡献者的署名天然保留，最符合 AGPL/Git 惯例；
- 对「想深度开发的人」友好，他们能沿着历史看你每一步为什么这么改。

不采用「补丁 + 子模块」的原因：构建链路会变复杂（需要额外一步打补丁），反而增加复刻门槛。

### 3.2 分支与标签约定

| 名称 | 用途 |
| --- | --- |
| `main` | 跟随上游（只做同步，不放自己的改动） |
| `apple` | 你的功能线，日常开发在这里 |
| `v0.7.20-apple.1` | 发布标签，与 `apple` 上对应提交一致 |
| `upstream/v0.7.20` 等 | 记录上游每个版本的同步点，便于回溯 |

> 上游标签形如 `v0.7.20`，你的标签统一加 `-apple.N` 后缀，避免与上游标签撞名。

### 3.3 README 顶部必须出现的三句话

1. 本项目基于 `<上游项目名>`（`<上游仓库地址>`，`<上游许可证>`）修改而来，感谢上游作者与所有贡献者。
2. 本项目是非官方衍生版本，与 `<上游项目名>` 官方无关；与 Apple Inc. 无任何关联，也未获其背书。
3. 本项目按 `<许可证>` 分发，完整源码见 `<本仓库地址>`。

（措辞模板会在 `02-README.md` 中给出可直接复制的版本。）

### 3.4 发布物清单

每次发布至少包含：

| 产物 | 说明 |
| --- | --- |
| 源码标签 | `v0.7.20-apple.1`（本次发布）；命名约定见 01 篇，后续为 `.2`、`.3`… |
| Release Notes | 变更 + 破坏性变更 + 已知问题 |
| 构建产物 | 安装包 / 免安装包（Windows x64） |
| 对应源码 | 标签页 `/archive/refs/tags/<tag>.zip` 或直接给标签链接（AGPL 第 6 条） |
| `CHANGELOG.md` 更新 | 逐条动机，不只列功能名 |

### 3.5 不要做的事

- 不要在二进制里删除或改写上游版权声明；
- 不要把 `LICENSE` 换掉；
- 不要在 README 里写「由我独立开发」；
- 不要在 Release 附件里只给二进制不给源码入口；
- 不要在文档/截图里露出自己的账号、邮箱、Cookie、真实路径与内网地址。
