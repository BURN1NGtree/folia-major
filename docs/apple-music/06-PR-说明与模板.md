# 06 · PR 说明与模板（可选）

> 一句话摘要：当前不建议把改动提回上游；若将来要提，本篇给出「怎么拆、怎么写、被拒怎么办」的最小可用模板。
>
> **实际要提 PR 时，直接用 [`PR-描述-草稿.md`](PR-描述-草稿.md)**：那是按上游 #357 / #419 的写法逐节对齐过的完整正文（动机、路线取舍、架构图、关键决策、已知限制、验证数字、待维护者定夺），可直接粘贴。本篇保留策略判断与拆分建议。

---

## 1. 先判断值不值得提

| 判断项 | 现状 | 结论 |
| --- | --- | --- |
| 改动是否侵入上游核心？ | 是：`App.tsx`、播放控制器、音源注册、账号规则、主进程 | 上游要审的东西多 |
| 是否跨进程/新增外部服务？ | 是：新增播控桥（Node 进程 + CDP） | 评审面扩大，还要讨论打包与端口 |
| 是否属于上游产品方向？ | 接入第三方商业音乐服务的网页端，属产品决策 | 上游可能直接拒 |
| 是否存在合规争议？ | 只驱动用户自身会话，但涉及 Apple 服务条款解释 | 上游可能出于风险回避拒收 |
| 维护成本对比 | 被接受 → 长期省事；被拒 → 仍要维护分叉 | 先按 fork 稳定，再谈 PR |

**建议**：等功能稳定（至少跑过一个上游版本周期）、把 Apple 逻辑收敛到独立目录、并且文档完整之后，再用「小步 PR」试探上游态度。

---

## 2. 如果要提：拆成哪几个 PR

不要一个巨型 PR。按「上游能独立接受」的最小单元切分，从**无争议**到**有争议**排序：

| 顺序 | PR 内容 | 上游接受可能性 | 备注 |
| --- | --- | --- | --- |
| 1 | 纯缺陷修复（如专辑歌手名映射、纯音乐歌词串首） | 高 | 与 Apple 无关，单独提最容易被收 |
| 2 | 音源 Provider 的注册机制泛化（不接 Apple，只让「新音源」更容易接入） | 中 | 需要与上游讨论抽象层设计 |
| 3 | 外部播放后端的抽象（把「谁出声」做成接口，先只接现有实现） | 中 | 这是接 Apple 的前置条件 |
| 4 | Apple 音源实现本身 | 低 | 依赖 2、3 先被合并 |
| 5 | 播控桥与专用浏览器 | 最低 | 涉及新进程、打包、服务条款，建议长期留在 fork |

每提一个 PR，先开 issue 说明动机与设计，避免「代码写完才被否」。

## 3. PR 描述模板

```markdown
## 这个 PR 做了什么

一句话：<一句话说清改动>

## 为什么需要

- 现状问题：<上游当前的行为>
- 本 PR 解决：<改完后的行为>
- 不解决的：<明确划界，避免评审期待错位>

## 实现思路

- 关键改动文件：
  - `src/xxx.ts` — <改了什么，为什么>
  - `src/yyy.ts` — <…>
- 是否涉及新增依赖：<无 / 有，名称与理由>
- 是否涉及主进程 / 打包配置：<是/否>

## 对现有行为的影响

- 默认行为是否改变：<否 / 是，说明范围>
- 是否需要迁移/设置项：<无 / 有>
- 性能影响：<实测或说明未测>

## 测试

- [ ] `npm run typecheck`
- [ ] `npm run test:unit`
- [ ] 手动验证：<步骤 + 预期>

## 截图 / 录屏

<占位>

## 合规说明

<若涉及第三方服务：说明只使用用户自身会话、不做解密与抓取；并说明是否默认关闭>

## 相关 issue

Closes #<编号>
```

## 4. 贡献流程注意

| 项 | 说明 |
| --- | --- |
| 贡献者协议 | 先看上游是否有 CLA/DCO 要求；没有则按「提交即同意以项目许可证授权」的惯例 |
| 提交规范 | 沿用上游的 commit 约定（如 `feat:`/`fix:`），不要混入本项目风格 |
| 分支 | 从上游 `main` 拉分支，**不要**把你的 fork 分支持续 rebase 后再提（评审看到的历史会非常乱） |
| 范围 | 一个 PR 只做一件事；纯格式化/重命名不要混进功能 PR |
| 被拒后 | 不要反复重提同一设计；先在上游 issue 里讨论抽象层，再决定是否继续 |

---

## 5. 被拒了怎么办

保持 fork 独立发布即可，代价是多一条同步线。为降低这个代价，日常开发遵循 `03-改动原理.md` 的「与上游同步」策略：Apple 逻辑尽量集中在独立文件，对上游文件的修改控制在「新增调用点」级别，减少合并冲突。
